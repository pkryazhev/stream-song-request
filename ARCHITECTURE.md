# Архитектура: Twitch Stream Companion

Личный инструмент-компаньон для стримов на Twitch. Стек: **Node.js / TypeScript**.

## Общий подход

Один локальный процесс (не микросервисы — это личный инструмент под одного пользователя), но с чёткой модульной структурой внутри: **event-driven монолит**. Модули общаются друг с другом только через общую шину событий (in-process EventEmitter / async event bus), а не напрямую — это позволяет добавлять новые фичи не трогая уже работающий код.

```
┌─────────────────────────────────────────────────────────┐
│                        Core                              │
│   EventBus · Config · Scheduler · Logger                 │
└───────┬───────────────┬──────────────────────────────────┘
        │               │
 ┌──────▼─────┐   ┌─────▼───────┐
 │  Twitch    │   │   Music     │
 │  Adapter   │   │   Adapter   │
 └──────┬─────┘   └─────┬───────┘
        │               │
        │        ┌──────▼───────┐
        │        │  Providers   │
        │        │  Spotify /   │
        │        │  YouTube /   │
        │        │  Yandex Music│
        │        └──────────────┘
        │
        └── чат-команды (!songrequest ...) → публикует событие song.requested

              ┌────────────┐        ┌────────────────┐
              │  SQLite    │        │  Web-сервер     │
              │  (очередь, │        │  (dashboard +   │
              │  история,  │        │  overlay-заглушка│
              │  настройки)│        │  на будущее)    │
              └────────────┘        └────────────────┘
```

## Core

- **EventBus** — общая шина событий (`song.requested`, `song.now_playing` и т.д.). Любой модуль публикует и подписывается, не зная о существовании других модулей напрямую.
- **Config** — токены API (Twitch, Spotify, Yandex Music), пути, настройки очереди.
- **Scheduler** — периодические задачи (например, обновление токенов OAuth).
- **Storage (SQLite)** — очередь треков, история заказов, забаненные пользователи/треки.

## Заказ и воспроизведение музыки — самая сложная часть

Раз источников несколько (**Spotify, YouTube, Яндекс Музыка**), ключевое архитектурное решение — ввести **единый интерфейс провайдера** и не завязывать очередь на конкретный сервис:

```ts
interface MusicProvider {
  id: 'spotify' | 'youtube' | 'yandex';
  search(query: string): Promise<TrackCandidate[]>;
  resolve(url: string): Promise<TrackCandidate | null>; // если прислали ссылку
  play(track: TrackCandidate): Promise<void>;
  pause(): Promise<void>;
  skip(): Promise<void>;
}
```

Каждый провайдер — отдельный модуль-адаптер под общим интерфейсом:

- **SpotifyProvider** — Spotify Web API + Spotify Connect. Управляет воспроизведением на устройстве, где залогинен Spotify (нужен Premium-аккаунт для управления воспроизведением через API). Плюс: не нужно ничего скачивать. Минус: играет через отдельное Spotify-приложение — отдельный источник звука для OBS.
- **YouTubeProvider** — поиск через YouTube Data API (или просто `ytsr`), получение аудио через `yt-dlp`, воспроизведение через локальный плеер (`mpv` с IPC-управлением, например `--input-ipc-server`). Плюс: нет ограничений по каталогу. Минус: юридически серая зона (скачивание аудио с YouTube нарушает ToS), это стоит держать в уме.
- **YandexMusicProvider** — официального публичного API у Яндекс Музыки нет, придётся использовать неофициальные библиотеки (например `yandex-music-api`/аналоги на npm) через токен из аккаунта. Это самое хрупкое звено — Яндекс может менять API без предупреждения, и это единственный провайдер, который может "сломаться" без явной причины.

**Важный практический момент — звук в OBS.** Если Spotify играет через нативное приложение, а YouTube/Яндекс — через `mpv`, то у тебя получается два разных источника аудио, которые OBS должен захватывать по отдельности (Application Audio Capture на оба процесса), либо свести их через виртуальный аудио-кабель (VB-Cable/VoiceMeeter) в один OBS-источник. Это стоит решить на этапе проектирования, а не постфактум — иначе очередь будет "прыгать" по звуку между разными громкостями/устройствами.

**Общая очередь:**
- `MusicAdapter` подписан на `song.requested` (публикуется `TwitchAdapter`-ом при разборе команды типа `!sr <запрос или ссылка>` в чате).
- По ссылке или домену определяется нужный провайдер (`resolve`), либо (если это текстовый запрос) — какой провайдер использовать по умолчанию/настройке пользователя.
- Трек кладётся в единую очередь в SQLite с полем `provider`, дальше воркер по очереди дёргает `play()` у нужного провайдера, дожидается окончания (событие от плеера или таймер по длительности трека) и берёт следующий.
- После начала воспроизведения публикуется `song.now_playing` → `TwitchAdapter` пишет в чат "сейчас играет: ...".
- Модерация: лимиты на пользователя, чёрный список треков/исполнителей, разрешить только определённых провайдеров — всё это конфигурируется в Core/Config, а не зашито в адаптерах.

## Структура проекта

```
/src
  /core          — event bus, config, scheduler, logger
  /db            — SQLite схема (миграции), доступ к данным
  /integrations
    /twitch      — chat, публикация событий
    /music
      /providers — spotify.ts, youtube.ts, yandex.ts (общий интерфейс)
      queue.ts   — воркер очереди
  /web           — dashboard (очередь музыки) + место под будущий overlay
/config          — токены, настройки (в .env / config.json, не в репозитории)
```

## Ключевые решения, зафиксированные сейчас

- Стек: Node.js/TypeScript, единый процесс.
- Музыка: три провайдера за одним интерфейсом `MusicProvider`, единая очередь в SQLite с полем `provider`.
- Нужно заранее решить схему сведения звука в OBS (виртуальный кабель или раздельный захват приложений) — иначе воспроизведение из разных источников будет несогласованным по звуку.
