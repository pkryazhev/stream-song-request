# stream-companion

Личный компаньон для стримов на Twitch. Реализовано:

1. **Заказ музыки через чат Twitch** (`!sr <ссылка или название трека>`), с
   проверкой фолловера, валидацией ссылки (YouTube/Spotify — либо
   текстовым поиском по Spotify, если ссылки нет) и переключением между
   дефолтным плейлистом Spotify и очередью заказов.
2. **Скип трека голосованием** (`!skip`) — стример скипает сразу, зрители —
   голосованием от числа активных в чате.
3. Spotify целиком необязателен — без него приложение просто работает в
   режиме "только YouTube" (см. раздел "Необязательная интеграция" ниже).

## Windows: запуск без консоли (bat-файлы)

В папке с приложением есть готовые `.bat`-файлы — их можно просто открывать
двойным кликом, набирать команды в консоли не нужно (Node.js и `mpv`/`yt-dlp`
всё равно должны быть установлены, см. ниже, но сами команды за тебя
запускают именно эти файлы):

- **`start.bat`** — обычный запуск приложения. При самом первом запуске,
  если `.env` ещё нет, сам создаст его из `.env.example` и откроет в
  Блокноте для заполнения — само приложение при этом ещё не стартует,
  нужно будет запустить `start.bat` ещё раз после того, как `.env` заполнен.
  Окно с логами не закрывается само по себе — заказ музыки печатает
  сообщения прямо туда, а любую ошибку можно спокойно прочитать, окно ждёт
  нажатия клавиши перед закрытием.
- **`setup-0-twitch-broadcaster-id.bat`** — спросит логин канала и покажет
  его числовой id для `TWITCH_BROADCASTER_ID` (нужен `TWITCH_CLIENT_ID`/
  `TWITCH_CLIENT_SECRET` в `.env`, заполненные заранее).
- **`setup-1-twitch-auth.bat`** — одноразовая авторизация Twitch (нужна
  всегда, без неё не будет работать ни чат, ни заказ музыки).
- **`setup-2-spotify-auth.bat`** — одноразовая авторизация Spotify (нужна,
  только если настраиваешь интеграцию со Spotify — см.
  "Необязательные интеграции" ниже).
- **`setup-3-spotify-devices.bat`** — покажет список устройств Spotify
  Connect для `SPOTIFY_DEVICE_NAME` (тоже только для Spotify).

Цифры в именах файлов — просто рекомендуемый порядок для самого первого
запуска, сами по себе они никак не связаны, каждый можно запускать отдельно
в любой момент. Дальше по тексту команды вида `npm run ...` — это то же
самое, что делают эти `.bat`-файлы, но напрямую в терминале; на Windows
удобнее пользоваться файлами, а команды пригодятся на macOS/Linux или если
уже работаешь в терминале.

## Особенность: без npm-зависимостей в коде приложения

Сам код ничего не устанавливает через `npm install` — используются только
встроенные возможности Node.js 22+: нативная поддержка TypeScript,
`node:sqlite`, `fetch`, `WebSocket`, `process.loadEnvFile()`, `node:test`.
Требуется Node.js **22.6+**. Проверить версию: `node --version`.

Для заказа музыки дополнительно нужны два **системных** (не npm) инструмента:

- **mpv** — локальный плеер, которым проигрываются YouTube-заказы;
- **yt-dlp** — mpv использует его под капотом, чтобы понимать YouTube-ссылки
  (отдельно скачивать файлы не нужно, mpv стримит через yt-dlp сам).

**Windows:** `winget install -e --id shinchiro.mpv` и `winget install -e --id yt-dlp.yt-dlp`
(либо через Scoop/choco). После установки закрой и заново открой терминал —
PATH обновляется только в новых окнах — и проверь `mpv --version` /
`yt-dlp --version`.

Важно про **обновление yt-dlp**: YouTube меняет формат страниц и правила
доступа очень часто (речь о неделях, не месяцах), и yt-dlp столь же часто
выпускает исправления — но `winget` подтягивает их с задержкой и иногда
путается в версиях (пишет, что обновление есть, хотя ты уже обновился
вручную, или наоборот). Поэтому если заказы с YouTube внезапно перестали
работать — **в первую очередь** обнови yt-dlp напрямую, а не через winget:
```powershell
yt-dlp -U
```
Если это не помогает или `yt-dlp -U` вообще недоступен — скачай последний
`yt-dlp.exe` напрямую со страницы релизов
(https://github.com/yt-dlp/yt-dlp/releases/latest) и either замени им файл,
который сейчас стоит в PATH, либо положи отдельно и укажи путь к нему через
`YTDLP_PATH` в `.env` — это подстрахует от случая, когда на машине по факту
несколько yt-dlp (например, старый от winget и рядом свежий .exe), и mpv
берёт не тот, что ты только что обновил.

**macOS:** `brew install mpv yt-dlp`

**Ubuntu/Debian:** `sudo apt install mpv` для mpv — но пакет `yt-dlp` в репозиториях
apt обычно устаревший (YouTube часто меняет формат страниц, и старый yt-dlp
из-за этого перестаёт работать). Надёжнее поставить и обновлять yt-dlp
отдельно от apt:
```bash
sudo curl -L https://github.com/yt-dlp/yt-dlp/releases/latest/download/yt-dlp -o /usr/local/bin/yt-dlp
sudo chmod a+rx /usr/local/bin/yt-dlp
```
Обновление в будущем — та же команда ещё раз, либо `yt-dlp -U`.

После установки проверь, что обе программы видны в PATH:
```bash
mpv --version
yt-dlp --version
```
Если `yt-dlp --version` не находится — mpv не сможет проигрывать YouTube-заказы,
даже если сам mpv установлен и работает.

**Если YouTube-заказ падает с ошибкой вида `Процесс плеера "mpv" завершился с
кодом 2`** — в логе теперь дополнительно печатается реальный вывод mpv/yt-dlp
(до этого он подавлялся флагом `--really-quiet`, и был виден только голый код
выхода). Смотри, что именно написано в выводе:

- **mpv вообще не понимает YouTube-ссылки / незнакомая ошибка** — почти
  всегда дело в версии yt-dlp. Обнови её способом из раздела про установку
  выше (`yt-dlp -U`, при необходимости — свежий `.exe` + `YTDLP_PATH`) и
  попробуй заказ ещё раз.
- **`Sign in to confirm you're not a bot`** — YouTube требует подтверждения,
  что запрос не от бота. Приложение по умолчанию уже пытается это обойти
  через `YOUTUBE_PLAYER_CLIENT` (см. `.env.example`). Если не помогает —
  добавь `YOUTUBE_COOKIES_FROM_BROWSER=firefox` (на Windows именно Firefox
  надёжнее всего для этого — не нужно закрывать браузер и нет проблем с
  шифрованием куки Chrome).
- **`The page needs to be reloaded`** — отдельная, тоже известная ошибка:
  так YouTube отвечает, когда конкретное сочетание "клиента" (см.
  `YOUTUBE_PLAYER_CLIENT`) и версии yt-dlp у него сейчас не в почёте. Сначала
  обнови yt-dlp (см. выше) — иногда этого достаточно. Если нет — попробуй
  другое значение `YOUTUBE_PLAYER_CLIENT`, например `web,web_safari,web_embedded`.
  Важно: если параллельно задан `YOUTUBE_COOKIES_FROM_BROWSER`/`_FILE`,
  клиент `tv` сам yt-dlp незаметно подменяет на `tv_downgraded` — если у
  тебя настроены и куки, и `player_client=tv`, и именно эта ошибка — попробуй
  временно убрать куки или сменить клиента.
- **`HTTP error 403 Forbidden`** — отличается от предыдущих тем, что
  случается уже ПОСЛЕ того, как ссылка на видео успешно нашлась (в выводе
  перед ней будет что-то вроде "Failed to open https://...googlevideo.com/
  videoplayback?..."). Причина — ссылка привязывается к IP, с которого её
  запросил yt-dlp; если сам mpv потом скачивает её с другого IP (типично на
  сетях, где есть и IPv4, и IPv6 одновременно — Windows может для разных
  запросов выбирать по-разному), YouTube отвечает 403. Особенно часто это
  бывает у "android"-клиентов (android, android_vr) — поэтому они по
  умолчанию не используются (см. `YOUTUBE_PLAYER_CLIENT` выше). Если всё
  равно случилось — попробуй `YOUTUBE_FORCE_IPV4=true` в `.env` (помогает не
  всегда: заставляет yt-dlp запрашивать ссылку по IPv4, но не гарантирует,
  что и сам mpv скачает именно по IPv4 — у него нет отдельной настройки под
  это). Если не помогло — последний вариант уже на уровне Windows: понизить
  приоритет/отключить IPv6 у сетевого адаптера (Панель управления → Сетевые
  подключения → свойства адаптера → снять галочку IPv6), это гарантированно
  убирает саму возможность рассинхронизации.
- Все три ошибки выше — это, по сути, текущее состояние "гонки вооружений"
  между YouTube и yt-dlp: то, что работает сегодня, через месяц может
  перестать, и наоборот. Если ничего из вышеперечисленного не помогло — стоит
  заглянуть в открытые issue на https://github.com/yt-dlp/yt-dlp/issues
  (поиск по тексту ошибки) — почти наверняка проблему уже обсуждают и там
  есть актуальный обходной путь.

Spotify-часть очереди (сами заказы с open.spotify.com) играет через Spotify
Connect API — там ничего локально ставить не нужно, но **обязателен Spotify
Premium**: обычный аккаунт не даёт Web API управлять воспроизведением.

## Необязательная интеграция (Spotify)

Spotify — необязателен, описывается своей группой переменных окружения в
`.env`: `SPOTIFY_CLIENT_ID` + `SPOTIFY_CLIENT_SECRET` + `SPOTIFY_DEFAULT_PLAYLIST_URI`.

Правило простое: заполняй группу целиком, либо не заполняй вовсе.

- **Не заполнена ни одна переменная группы** — интеграция отключается, при
  старте будет разовое предупреждение в лог, остальное приложение работает
  как обычно. Без Spotify заказ музыки работает только по YouTube-ссылкам
  (текстовый поиск трека и ссылки на Spotify перестают приниматься, `!sr`
  отвечает соответствующим сообщением).
- **Заполнена только часть переменных группы** — приложение откажется
  стартовать и укажет, каких переменных не хватает. Это осознанное решение:
  частично заполненная группа почти всегда означает недосмотр (забыли
  дописать один токен), и лучше узнать об этом сразу при старте, а не
  посреди стрима.

## Установка

1. Убедись, что стоит Node.js 22.6+, а также `mpv` и `yt-dlp` (см. выше).
2. Скопируй `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```
3. Заполни `.env` — подробные комментарии есть в самом файле, но по шагам:

   **Twitch (общее)**
   - `TWITCH_CLIENT_ID` / `TWITCH_CLIENT_SECRET` — зарегистрировать приложение на
     https://dev.twitch.tv/console/apps. В OAuth Redirect URLs добавь
     `http://localhost:8889/callback`. Важно: именно `localhost`, а не
     `127.0.0.1` — с ним Twitch выдаёт ошибку "URL-адреса должны
     использовать протокол HTTPS" (для http Twitch разрешает только
     буквально `localhost`; у Spotify ниже правило обратное).
   - `TWITCH_BROADCASTER_LOGIN` — логин канала.
   - `TWITCH_BROADCASTER_ID` — узнать после того как заполнишь Client ID/Secret:
     на Windows проще всего `setup-0-twitch-broadcaster-id.bat` (см. выше),
     либо в терминале:
     ```bash
     node scripts/twitch-user-id.ts <TWITCH_BROADCASTER_LOGIN>
     ```

   **Заказ музыки — чат**
   - `TWITCH_CHAT_BOT_USERNAME` — от чьего имени бот пишет в чат. Если это ты
     сам — тот же логин, что и `TWITCH_BROADCASTER_LOGIN`. Если отдельный
     бот-аккаунт — он должен быть модератором канала.
   - `MUSIC_COMMAND` (по умолчанию `!sr`), `MUSIC_MIN_FOLLOWER_DAYS` (по умолчанию `3`).
   - `MUSIC_SKIP_COMMAND` (по умолчанию `!skip`), `MUSIC_SKIP_THRESHOLD_PERCENT`
     (по умолчанию `30`), `MUSIC_SKIP_ACTIVE_WINDOW_MS` (по умолчанию 10 минут) —
     скип текущего заказа, см. "Как работает скип" ниже.

   **Заказ музыки — YouTube**
   - `YOUTUBE_API_KEY` — API-ключ с включённым YouTube Data API v3:
     https://console.cloud.google.com/apis/credentials (обычный API-ключ, не OAuth).
   - `YOUTUBE_PLAYER_CLIENT` — если mpv при заказе падает с ошибкой вида
     `Sign in to confirm you're not a bot` или `The page needs to be
     reloaded` (это про локальное воспроизведение через mpv/yt-dlp, никак
     не связано с `YOUTUBE_API_KEY` выше) — значение по умолчанию уже
     пытается это обходить, но раз YouTube меняет правила постоянно, могут
     понадобиться `YOUTUBE_COOKIES_FROM_BROWSER`/`YTDLP_PATH` из
     `.env.example` — там же подробный разбор обеих ошибок.
   - `MPV_VOLUME` (по умолчанию `50`) — громкость mpv при старте YouTube-заказа
     (0-100), чтобы не оглушало после Spotify.

   **Заказ музыки — Spotify** (необязательно — см. "Необязательные интеграции" выше)
   - `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` — приложение на
     https://developer.spotify.com/dashboard. В Redirect URIs добавь
     `http://127.0.0.1:8888/callback`. Важно: именно `127.0.0.1`, а не
     `localhost` — у Spotify для http принимается только IP-адрес
     loopback (правило обратное Twitch-у выше).
   - `SPOTIFY_DEFAULT_PLAYLIST_URI` — дефолтный плейлист. Проще всего:
     в Spotify у плейлиста `...` → Share → Copy link to playlist — обычную
     ссылку вида `https://open.spotify.com/playlist/<id>?si=...` можно
     вставить как есть, приложение само приведёт её к нужному виду
     (см. `src/music/spotifyPlaylistUri.ts`). "Copy Spotify URI" тоже
     подойдёт, если она у тебя есть — но эта опция то пропадает, то
     появляется в разных версиях Spotify, поэтому полагаться на неё не стоит.
   - Если Spotify настроен, `!sr` дополнительно принимает текстовый запрос
     вместо ссылки (например `!sr Rick Astley - Never Gonna Give You Up`) —
     заказывается первый результат поиска в Spotify по этому тексту
     (см. "Как работает заказ музыки" ниже).

4. Пройди одноразовую авторизацию (открывает ссылку — нужно один раз
   разрешить доступ в браузере, токены с refresh сохранятся на диск). На
   Windows — `setup-1-twitch-auth.bat` и `setup-2-spotify-auth.bat` (см.
   выше), либо в терминале:
   ```bash
   npm run auth:twitch     # чат + проверка фолловеров — всегда нужно
   npm run auth:spotify    # управление воспроизведением — только если настроил Spotify (см. выше)
   ```

5. Если настроил Spotify: открой его (desktop/mobile/web) на устройстве, где
   должна играть музыка на стриме, и узнай его точное имя — на Windows
   `setup-3-spotify-devices.bat`, либо в терминале:
   ```bash
   npm run devices:spotify
   ```
   Впиши это имя в `SPOTIFY_DEVICE_NAME` в `.env`. Это не строго
   обязательно, но без этого Spotify Web API требует, чтобы у аккаунта
   уже было "активное устройство" — иначе запуск плейлиста падает с
   `HTTP 404` ("нет активного устройства"), даже если Spotify открыт.
   С `SPOTIFY_DEVICE_NAME` приложение явно указывает Spotify, где играть,
   и это работает, даже если на устройстве сейчас ничего не играет —
   достаточно, чтобы Spotify был просто запущен.

## Запуск

На Windows проще всего двойным кликом по `start.bat` (см. "Windows: запуск
без консоли" выше) — или по `start-paused.bat`, если нужно сразу поднять
приложение с приостановленными заказами музыки (тот же `start.bat`, но с
флагом `-s`, см. "Приостановка заказов" ниже). В терминале (любая ОС):

```bash
npm start        # обычный запуск
npm run dev       # с автоперезапуском при изменении файлов (node --watch)
npm start -- -s   # запуск сразу с приостановленными заказами музыки (см. ниже)
```

### Как работает заказ музыки

1. Зритель пишет в чат `!sr <ссылка или название трека>`.
2. Проверяется, что он фолловер канала от `MUSIC_MIN_FOLLOWER_DAYS` дней —
   если нет, бот отвечает и на этом всё. **Исключение — сам broadcaster**:
   Twitch не позволяет зафолловить собственный канал, поэтому для аккаунта
   стримера эта проверка пропускается вообще (определяется по бейджу
   `broadcaster` в чате, а не по имени пользователя).
3. Ссылка должна быть на YouTube или Spotify-трек. Если это не похоже на
   ссылку вообще и Spotify настроен — приложение ищет трек в Spotify по
   тексту (например `!sr Rick Astley - Never Gonna Give You Up`) и
   заказывает первый результат поиска — то же самое, что показал бы поиск в
   самом приложении Spotify первым пунктом. Если результатов вообще нет —
   "ссылка невалидная". Если Spotify не настроен — принимаются только
   ссылки на YouTube.
4. Для YouTube дополнительно проверяется длительность (по умолчанию не
   больше 10 минут, `YOUTUBE_MAX_DURATION_SEC`).
5. Валидный заказ кладётся в конец очереди (SQLite), бот подтверждает в
   чат: `трек добавлен в очередь: "..." (позиция N)`. Для YouTube это просто
   название видео, для Spotify — "Исполнитель - Название" (у Spotify-трека
   почти всегда есть чёткое поле исполнителя, а без него не всегда понятно,
   о каком именно треке речь — мало ли одноимённых каверов и ремиксов).
6. Пока очередь пуста, в Spotify играет дефолтный плейлист
   (`SPOTIFY_DEFAULT_PLAYLIST_URI`, если Spotify настроен). Как только
   текущий трек дефолтного плейлиста подходит к концу и в очереди есть
   заказ — вместо следующего трека плейлиста включается заказ (то есть
   текущий трек всегда доигрывает до конца, ничего не обрывается). Если
   Spotify не настроен, дефолтного плейлиста просто нет — заказ из очереди
   начинает играть сразу, как только освобождается плеер.
7. Заказы играют строго по очереди (FIFO, без приоритетов) — Spotify-заказы
   через Spotify Connect, YouTube-заказы через mpv (со стартовой громкостью
   `MPV_VOLUME`, по умолчанию 50%, чтобы не оглушало после Spotify). Перед
   YouTube-заказом Spotify явно ставится на паузу (Spotify Connect и mpv —
   два независимых плеера, и без явной паузы дефолтный плейлист играл бы
   поверх YouTube-заказа) — сбой самой паузы (например, сеть) не отменяет
   заказ, YouTube всё равно запускается.
8. Когда очередь опустела — снова запускается дефолтный плейлист (если
   Spotify настроен).

### Как работает скип (`!skip`)

- Если команду пишет сам стример — текущий заказ скипается сразу, без
  голосования (проще всего сообразить, зачем это может понадобиться —
  YouTube-заказ иначе не переключить, в отличие от Spotify).
- Если команду пишет тот же зритель, который этот трек и заказал — тоже
  скипается сразу, без голосования (это его собственный заказ, разумно, что
  он может передумать без порога). Право на мгновенный скип действует
  только для трека, который сейчас реально играет — если зритель заказал
  что-то в очередь, но играет ещё не его заказ, обычный `!skip` от него
  идёт в общее голосование, как от любого другого зрителя.
- Если пишет кто-то ещё — это голос. Трек скипается, когда голосов наберётся
  не меньше `MUSIC_SKIP_THRESHOLD_PERCENT` процентов (по умолчанию 30%,
  округление вверх) от числа **активных** в чате — уникальных зрителей,
  написавших что-либо (не обязательно `!skip`) за последние
  `MUSIC_SKIP_ACTIVE_WINDOW_MS` (по умолчанию 10 минут). Общее число
  зрителей стрима приложению взять неоткуда (это не то же самое, что число
  подключённых к чату), поэтому порог считается именно от активности в чате.
- Голоса за конкретный трек сбрасываются, как только начинает играть
  следующий заказ.
- Скип работает, только пока реально играет заказ — во время дефолтного
  плейлиста скипать нечего, бот ответит соответствующим сообщением.
- Для YouTube-заказа скип останавливает mpv-процесс напрямую. На Windows это
  делается через `taskkill /T /F` (а не обычный `child.kill()`) — Node.js на
  Windows лишь эмулирует POSIX-сигналы, и обычный `kill()` останавливает
  только сам процесс mpv, но не его дочерний процесс yt-dlp (mpv запускает
  его сам, чтобы разобрать ссылку) — из-за этого раньше "скипнутый" mpv мог
  не закрыться до конца и продолжить играть параллельно со следующим
  треком. `/T` останавливает всё дерево процессов, `/F` — принудительно.
  Для Spotify-заказа приложение не прерывает сам трек через Spotify API —
  вместо этого досрочно завершается внутреннее ожидание конца трека, и
  оркестратор сразу переходит к следующему заказу (или дефолтному
  плейлисту), что и так явно указывает Spotify, что играть дальше.

### Приостановка заказов (`!pr` / `!rr`)

Доступно только стримеру и модераторам.

- `!pr` — приостанавливает приём новых заказов (зрителям бот отвечает, что
  заказы сейчас недоступны) и останавливает дефолтный плейлист Spotify, если
  он в этот момент играет. Уже принятые в очередь заказы никуда не деваются
  и доигрывают как обычно — команда останавливает именно приём новых.
- `!rr` — снова разрешает заказы и, если очередь пуста, тут же перезапускает
  дефолтный плейлист (не дожидаясь обычного опроса раз в
  `SPOTIFY_POLL_INTERVAL_MS`).
- Флаг `-s` (или `--pause-requests`) при запуске приложения — то же самое, что
  сразу набрать `!pr` после старта, но без похода в чат (например, если перед
  стримом заведомо нужна техническая пауза). Включить заказы обратно можно
  командой `!rr` в чате. На Windows для этого есть отдельный `start-paused.bat`
  рядом с обычным `start.bat` — двойной клик по нему запускает приложение
  сразу с этим флагом, ничего вручную вписывать не нужно.

### Про звук YouTube-заказов в OBS

YouTube-заказы играют через отдельный процесс mpv — сам код не может
"подключить" его звук к OBS напрямую, это обычная задача роутинга звука на
уровне ОС/OBS, не специфичная для этого приложения. Но приложение умеет
направить звук mpv на конкретное аудио-устройство через `MPV_AUDIO_DEVICE`
в `.env` (см. `.env.example`) — этого вместе с виртуальным аудио-кабелем
достаточно, чтобы в OBS ловить звук именно YouTube-заказов отдельно от
остального. Подробно, по шагам (Windows, с [VB-CABLE](https://vb-audio.com/Cable/)):

1. **Поставь VB-CABLE**, если ещё не сделал (бесплатно, ссылка выше —
   раздел Donationware, скачать архив, распаковать, запустить
   `VBCABLE_Setup_x64.exe` от имени администратора, перезагрузить Windows
   после установки — без перезагрузки новое устройство иногда не подхватывается).
   VB-CABLE добавляет в Windows пару виртуальных устройств: **CABLE Input**
   (устройство "воспроизведения" — на него приложения ОТПРАВЛЯЮТ звук) и
   **CABLE Output** (устройство "записи" — с него можно этот же звук
   ЗАБРАТЬ, например в OBS). По сути это провод между двумя розетками.

2. **Узнай точное имя устройства для mpv.** Открой командную строку
   (Win+R → `cmd` → Enter) и выполни:
   ```
   mpv --audio-device=help
   ```
   Если команда не находится — впиши в неё полный путь к `mpv.exe` вместо
   `mpv`. В выводе найди строку, где в скобках упоминается `CABLE Input`,
   например:
   ```
   'wasapi/{05a4a939-...-...-...-............}' (CABLE Input (VB-Audio Virtual Cable))
   ```
   Тебе нужна именно часть в одинарных кавычках —
   `wasapi/{05a4a939-...}`.

3. **Впиши это значение в `.env`**:
   ```
   MPV_AUDIO_DEVICE=wasapi/{05a4a939-...-...-...-............}
   ```
   (без одинарных кавычек — просто сам текст). Перезапусти приложение
   (`start.bat` — см. "Windows: запуск без консоли"), чтобы .env
   перечитался.

4. **Проверь заказом.** Закажи что-нибудь через `!sr <ссылка на YouTube>` —
   звук из колонок/наушников напрямую слышно быть не должно (он теперь
   уходит только в CABLE Input) — это ожидаемо, а не баг, звук просто ждёт
   в "проводе" на выходе CABLE Output.

5. **В OBS добавь источник звука.** Источники → `+` → **"Захват вывода
   аудио" (Audio Output Capture)** → в качестве устройства выбери
   **CABLE Output**. Теперь в сцене есть отдельная звуковая дорожка именно
   YouTube-заказов — её видно и регулируется отдельно в микшере аудио OBS,
   независимо от остального звука.

6. **Чтобы слышать заказы самому (мониторинг), а не только зрителям** —
   иначе ты не будешь слышать, что играет:
   - В OBS: правой кнопкой по добавленному источнику `CABLE Output` →
     **Свойства аудио** (Advanced Audio Properties) → **Аудио мониторинг**
     (Audio Monitoring) → выбери **"Мониторинг и вывод"** (Monitor and Output).
   - Один раз в целом по OBS: Настройки → Аудио → Дополнительно →
     **Устройство мониторинга** (Monitoring Device) — укажи свои
     наушники/колонки. После этого звук из CABLE Output будет идти и в
     стрим, и тебе в наушники через сам OBS — без обратной петли и
     задержки, в отличие от варианта "Прослушивать это устройство" в
     настройках звука Windows (тоже сработает, но добавляет лишнюю
     задержку и звук не пройдёт через микшер OBS).

Поскольку направляется звук именно mpv (через `MPV_AUDIO_DEVICE`), а не всё
устройство вывода Windows целиком — Spotify, звук Discord и всё остальное
как играло в обычные колонки/наушники, так и продолжает — трогать
"устройство по умолчанию" в Windows не нужно вообще.

На macOS аналогичную роль играет [BlackHole](https://github.com/ExistentialAudio/BlackHole)
или [Loopback](https://rogueamoeba.com/loopback/) — принцип тот же: узнать
точное имя устройства (`mpv --audio-device=help` работает и там), вписать
его в `MPV_AUDIO_DEVICE`, дальше OBS захватывает его так же через Audio
Output Capture.

## Тесты

```bash
npm test
```

Юнит-тестами покрыто всё, что не требует реальной сети/аккаунтов: разбор
ссылок (YouTube/Spotify/невалидные), разбор Twitch IRC-протокола, разбор
длительности YouTube, FIFO-очередь в SQLite, обработчик заказа целиком
(follower-check → валидация → постановка в очередь → ответ в чат — на
подменённом `fetch`), state machine переключения default/очередь
(на фейковых Spotify/YouTube-плеерах), обёртка над процессом-плеером
(реальный `node`-процесс вместо mpv). Реальные сетевые вызовы (Twitch IRC
WebSocket, живые Spotify/YouTube API, сам mpv) тестами не покрыты — их
можно проверить только на твоей машине с реальными токенами и `mpv`/`yt-dlp`
в PATH.

## Известные ограничения / осознанные решения

- YouTube-заказы играют через mpv — у него есть настоящий сигнал о конце
  трека (mpv-процесс сам завершается), поллинг тут не нужен вообще.
- У Spotify Web API нет push-уведомлений о смене трека (обычный REST) —
  поэтому статус приходится опрашивать. Но раз каждый опрос и так
  возвращает duration/progress, оркестратор не ждёт вслепую фиксированный
  `SPOTIFY_POLL_INTERVAL_MS` — он считает, сколько миллисекунд реально
  осталось до конца трека, и планирует следующую проверку точно на этот
  момент (см. `scheduleNearEndCheck` в `playbackOrchestrator.ts`). Это не
  настоящий push от Spotify, но по факту ведёт себя так же точно и не
  зависит от того, насколько часто настроен обычный опрос. `SPOTIFY_POLL_INTERVAL_MS`
  при этом всё ещё используется как "обычный" интервал (для общих
  проверок и первой паузы после запуска трека), а `SPOTIFY_END_THRESHOLD_MS`
  всегда приводится к значению не меньше него — просто как дополнительная
  подстраховка, если что-то настроено совсем нестандартно.
- Пока играет Spotify-заказ, ожидание его конца устойчиво к единичным сбоям
  сети (обрыв соединения, TLS-хендшейк и т.п. — `fetch failed`/`ECONNRESET`):
  такой сбой просто логируется и опрос продолжается, а не обрывает заказ
  раньше времени. Если сбои идут подряд 5 раз — ожидание прекращается, чтобы
  не зависнуть навсегда, и включается дефолтный плейлист.
- Если `TWITCH_CHAT_BOT_USERNAME` — не сам broadcaster, этот аккаунт должен
  быть модератором канала, иначе Twitch не даст скоуп `moderator:read:followers`.
- `node:sqlite` и `WebSocket` в Node помечены experimental/новыми — печатают
  предупреждение при старте, это безопасно игнорировать.
- Скачивание аудио с YouTube через yt-dlp формально в серой зоне ToS
  YouTube — это личный инструмент для собственного стрима, но стоит иметь в виду.
- Порог голосования за скип (`MUSIC_SKIP_THRESHOLD_PERCENT`) считается от
  числа уникальных зрителей, писавших в чат за последние
  `MUSIC_SKIP_ACTIVE_WINDOW_MS` — а не от общего числа зрителей стрима,
  которое приложению взять неоткуда (Twitch не отдаёт список зрителей чата
  через используемые здесь API).
- Скип Spotify-заказа не останавливает сам трек через Spotify API — он лишь
  досрочно завершает внутреннее ожидание, после чего оркестратор сам
  указывает Spotify, что играть дальше (следующий заказ или дефолтный
  плейлист). Разница не должна быть заметна на слух — переключение
  происходит сразу же, — но стоит иметь в виду, если будешь читать код.
- Звук YouTube-заказов (через mpv) не подключается к OBS автоматически —
  это отдельная задача роутинга аудио на уровне ОС, см. "Про звук
  YouTube-заказов в OBS" выше.
